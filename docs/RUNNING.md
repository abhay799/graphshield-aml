# GraphShield AML — Local Runbook

This document is the project’s honest local-run guide. It describes how to set up the repository, start the API/UI, run deterministic demo scenarios, and inspect historical certification evidence without claiming production status.

## 1. Supported environment

### Repository evidence

The repo’s current source/docker configuration points to Python 3.12:
- `Dockerfile` uses `FROM python:3.12-slim`
- `docker-compose.yml` is configured for the same runtime shape

The validation docs also note a historical mismatch: older snapshots mention Python 3.14.5, but that is not fresh proof that 3.14 is the supported local runtime. The best current evidence is 3.12.

Use the following as the working baseline:
- Python: 3.12.x
- OS: Windows 10/11 PowerShell is the primary tested path
- Linux/macOS: the same project structure is generally valid, but the repo’s concrete examples and local commands are written for Windows PowerShell
- Virtual environment: required, local repo venv

Do not claim support for a Python version simply because it was used historically in a prior artifact snapshot.

### Shell conventions

Use PowerShell for the commands below unless you are already working in a Unix shell. The repo’s short local commands are written to match that path.

## 2. Clone and environment setup

From a shell with Git available:

```powershell
git clone <repo-url>
cd <repo-folder>
git checkout graphshield-v2
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
```

Install the project dependencies using the repo’s existing files:

```powershell
python -m pip install -r requirements-core.txt
python -m pip install -r requirements-ml.txt
```

The repository also contains:
- `requirements-runtime.txt` — combined runtime stack
- `requirements-gpu.txt` — GPU/TGN work only

If you want a single local runtime install, the repo’s combined file is the most direct choice:

```powershell
python -m pip install -r requirements-runtime.txt
```

This is the local project baseline. It is not a claim that the full historical cloud or GPU stack is required for every developer workflow.

## 3. Required local artifacts

The repository is not fully self-contained. Several runtime artifacts are intentionally ignored and must be present locally for a realistic demo or analyst workflow.

### REQUIRED FOR FULL DEMO

These are the primary runtime assets expected by the local API/UI:

- `data/processed/`
  - `cases/case_queue.parquet`
  - `cases/case_paths.jsonl`
  - `cases/bundles/*.json`
  - `cases/evidence_documents.*`
  - `graph/*.parquet`
  - `explanations/`
  - `entities/`
- `models/`
  - model binaries and calibration artifacts if present locally
- `data/policy/`
  - locally indexed policy retrieval corpus if the retrieval workflow is being exercised
- case-store and evidence state (generated by pipeline)
  - `data/processed/cases/case_store.duckdb`
  - any added DuckDB/SQLite local state created by the ingestion or case workflows

Without these, the API is still importable, but the analyst workflow will not have the expected case, graph, and evidence data.

### OPTIONAL

These are not required for the basic API/UI startup path:

- GPU/TGN cloud materials under `kaggle_*` and `temp_cloud_kit/`
- `docker-compose.yml` integration services
- Neo4j / Redis / Kafka / Redpanda / MinIO / MLflow / Prometheus / Grafana / Keycloak components
- cloud GPU training bundles and distributed runtime artifacts

### GENERATED BY PIPELINE

These are produced by earlier project phases and should be treated as generated artifacts rather than manually edited inputs:

- processed Parquet tables
- case bundles
- case paths
- evidence documents
- model metrics reports
- certification JSON and markdown reports
- scenario output artifacts under `docs/demo/`

Do not treat these as a fresh ground truth unless you have rerun the pipeline in the same environment and recorded the result.

### Important boundary

The repo intentionally does not include a single private lockfile or a complete artifact registry. A fresh clone is not enough to reproduce the entire runtime without the required local files or approved artifact handoff.

## 4. Start the API

The actual FastAPI entrypoint in the repo is:

```powershell
cd <repo-folder>
.\.venv\Scripts\Activate.ps1
python -m uvicorn api.app:app --app-dir src --host 127.0.0.1 --port 8000
```

This matches the repo’s app structure and the API modules under `src/api/`.

### Expected result

- API host: `http://127.0.0.1:8000`
- Docs: `http://127.0.0.1:8000/docs`
- Health endpoint: `http://127.0.0.1:8000/health`

Quick verification:

```powershell
Invoke-WebRequest http://127.0.0.1:8000/health -UseBasicParsing
```

The repo’s health endpoint returns a JSON payload with fields such as:
- `status`
- `service`
- `mode`
- `case_queue_rows`
- `champion`

The service is explicitly read-only and decision-support only.

## 5. Start the UI

The Streamlit entrypoint is the analyst frontend:

```powershell
cd <repo-folder>
.\.venv\Scripts\Activate.ps1
$env:GRAPHSHIELD_API_URL="http://127.0.0.1:8000"
python -m streamlit run src\frontend\app.py --server.port 8502
```

### Expected browser URL

- `http://localhost:8502`
- `http://127.0.0.1:8502`

### Provenance/fallback behavior

The frontend reads through `src/frontend/provider.py` and is designed to fall back to local read-only artifacts if the API is unavailable. Provenance labels intentionally distinguish between:
- `BACKEND API`
- `LOCAL READ-ONLY ARTIFACT`
- `NOT CONNECTED`

This keeps the demo and UI honest without pretending the runtime is live when only local artifacts are available.

## 6. Run deterministic demo scenarios

The repo includes a deterministic demo runner for the Step 4 scenario package.

### List scenarios

```powershell
python scripts/demo/run_scenarios.py --list
```

Expected IDs:
- `GS-AML-001`
- `GS-AML-002`
- `GS-AML-003`
- `GS-AML-004`

### Run one scenario

```powershell
python scripts/demo/run_scenarios.py --scenario GS-AML-001
```

### Run all scenarios

```powershell
python scripts/demo/run_scenarios.py --scenario all
```

### PowerShell wrapper

```powershell
.\scripts\demo\run_scenarios.ps1 --scenario all
```

### Expected output file

- `docs/demo/scenario_run_output.json`

This file is deterministic and repository-backed. It is designed to reflect the local, read-only case queue, path evidence, graph evidence, and bundle review gates without inventing new outputs.

### Determinism and provenance

The scenario runner is expected to be stable across reruns because it uses fixed repository inputs and no random identifiers. It classifies its output as:
- `LOCAL READ-ONLY ARTIFACT`
- `STATIC DEMO`

It does not claim live model scoring, external deployment, or regulatory action.

## 11. Runtime boundaries and honest use

The repository should be used as a decision-support and evidence review prototype. It is not a live compliance engine.

Current runtime boundaries from repo evidence:
- read-only services
- human review required
- no autonomous account blocking
- no autonomous case closure
- no automatic SAR/STR filing
- no automatic regulatory submission
- no claim of production SLO attainment
- no claim of external cloud smoke/live deployment

If you are running locally, treat the repo as a reproducible developer demo and evidence package rather than a production-grade AML operating system.
