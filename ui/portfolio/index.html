Research / portfolio safety boundary

GraphShield AML is a research / portfolio decision-support platform. Use public or synthetic data only for portfolio/academic demonstrations. It supports human review; it is not a production fraud-detection or AML enforcement system.

It does not autonomously block transactions or accounts, close cases, file regulatory reports (including SAR/STR), or replace legal/compliance judgment. Human review remains required for investigation outcomes.

Signal boundary: First-time/unknown accounts have structurally limited signal because historical, pair, velocity, and network context may not exist yet. The result is decision-support demo output, not an enforcement or compliance decision.
Public research demo: live transaction scoring is deployed on Railway. Runtime history is Redis-backed and forward-only; synthetic/research demo only.

Import Bank Statement

Import a sample or anonymized CSV/XLSX/XLS statement locally in the browser. GraphShield auto-detects common date, narration, debit, credit, amount, reference and payment-mode columns, hashes counterparties and references, then converts the result into the existing scoring schema.

Your original statement file is not uploaded by this importer.

Do not use an unredacted real bank statement in this public demo. Use a sample or anonymized copy with personal and account-identifying information removed.

Raw narration, names, UTR/reference values and account numbers should not be sent to the scoring API. Use a non-identifying account alias below. Counterparty text and detected references are hashed locally before converted rows are loaded into the scoring table.

Choose a CSV/XLSX/XLS statement, then analyze it locally.

Historical statement timestamps cannot be sent directly to the shared forward-only live scorer. Loading creates an explicit synthetic demo projection at the current live time while preserving row order, amounts, direction and anonymized counterparties. It is not historical point-in-time scoring.

CSV schema and execution help

Required case-sensitive headers, in any order:

transaction_id,event_ts,from_bank,from_account,to_bank,to_account,amount_paid,amount_received,payment_currency,receiving_currency,payment_format

UTF-8 CSV ? maximum 256 KiB ? 100 nonblank records (including invalid rows) ? 32 columns ? 1024 characters per cell. Extra non-label columns are ignored and never sent.

Required cells cannot be blank. Identifiers retain leading zeros and case. Amounts must be finite nonnegative decimals without currency symbols or grouping separators.

Use YYYY-MM-DDTHH:mm:ss with optional fractional seconds (up to 6 digits), Z or ?HH:mm. If no timezone offset is provided, the backend interprets the timestamp as UTC. Timestamps and offsets are preserved in requests.

Duplicate transaction IDs are rejected because the scoring endpoint is stateful and does not provide transaction-ID idempotency.

Valid rows must have nondecreasing UTC timestamps. Rows are never automatically sorted. Equal timestamps remain in CSV order; separate requests do not reproduce complete timestamp-group offline parity.

Batch scoring is an ordered sequence of live scoring requests and is not an atomic historical replay.

Stopping prevents future submissions only. Already submitted transactions cannot be rolled back by the browser. No automatic retry occurs. Timeout or connection loss can leave backend completion uncertain; further scoring in this page is disabled after an uncertain batch request.

Use the Scoring API URL above. Existing Redis history and other clients can affect results. Check backend completion before reloading after uncertainty; reload does not clear Redis or undo transactions.
